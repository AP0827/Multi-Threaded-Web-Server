MTWS - MULTITHREADED SECURE HTTP SERVER
Consolidated Requirements for Academic Submission
May 2026

==============================================
1. PROJECT OVERVIEW
==============================================

MTWS is an educational HTTP/1.1 server implemented in Go, designed to demonstrate network
security concepts and HTTP compliance through:
● Custom HTTP/1.1 parser with strict RFC 7230-7231 compliance
● Web Application Firewall (WAF) with signature-based threat detection
● Per-IP token bucket rate limiting for DoS protection
● Worker pool concurrency with buffered job queue architecture
● Side-by-side security benchmarking against nginx + ModSecurity
● Load testing and performance metrics collection

Target Deployment: Single-machine classroom labs, security research, educational demonstrations.

4. FUNCTIONAL REQUIREMENTS
==============================================

Network Protocol & Connection Handling
● TCP Connection Acceptance: Server accepts incoming TCP connections on configurable port
  (default 8080). Connections handed off to worker pool for HTTP request processing.
  Status: Implemented. Evidence: cmd/server/main.go (net.Listen, Accept loop)
  
● HTTP/1.1 Request Parsing: Strict compliance with RFC 7230-7231. Parses request line,
  headers, body (Content-Length and Transfer-Encoding: chunked), and optional trailers.
  Size limits enforced: request line 4096 bytes, header line 8192 bytes, max 64 headers,
  body 1 MiB. Fail-closed approach: rejects ambiguous requests with 400 Bad Request.
  Status: Implemented. Evidence: http/parser.go, http/request.go + parser_test.go,
  parser_fuzz_test.go

● HTTP Response Generation: Generates responses with appropriate status codes (200 OK,
  400 Bad Request, 403 Forbidden, 404 Not Found, 500 Internal Server Error) and headers.
  Automatic Content-Length computation; optional Date and Content-Type headers.
  Status: Implemented. Evidence: core/response.go

● Request Routing: Exact path matching to registered handlers. Returns 404 Not Found
  if path not in routes. Supports dynamic handler registration at startup.
  Status: Implemented. Evidence: core/router.go

● Connection Closure: Closes socket after response sent. Clean resource cleanup via
  Go defer mechanisms. Handles client-initiated closes gracefully.
  Status: Implemented. Evidence: core/connection.go (defer conn.Close())

Concurrency & Job Queue Architecture
● Worker Pool: Fixed-size pool of goroutines (configurable, default 10 workers) for
  bounded concurrency control. Prevents goroutine explosion under high load. Configurable
  via MTWS_WORKER_POOL_SIZE and MTWS_JOB_QUEUE_SIZE environment variables.
  Status: Implemented. Evidence: pool/pool.go, cmd/server/main.go

● Buffered Job Queue: Accepts connection jobs into buffered channel (configurable,
  default capacity 200). Provides natural backpressure: listener blocks when queue full,
  workers block when queue empty. No unbounded goroutine creation.
  Status: Implemented. Evidence: pool/pool.go (Job struct, StartWorkerPool function)

● Connection-to-Job Dispatch: Listener accepts connection, extracts client IP, performs
  rate limiter decision, posts Job to queue if allowed, or closes connection if denied.
  Status: Implemented. Evidence: cmd/server/main.go (Accept loop + rate limiter check)

Security & Rate Limiting
● Per-IP Rate Limiting (Token Bucket): One token bucket per unique client IP.
  Configurable refill rate (default 5.0 tokens/sec) and burst capacity (default 10.0 tokens).
  Decision logic: if tokens ≥ 1, deduct 1 and allow request; else deny and close connection.
  Disable via environment variables MTWS_RATE_LIMIT_DISABLED or MTWS_BENCHMARK_MODE.
  Status: Implemented. Evidence: security/ratelimiter/limiter.go

● WAF (Web Application Firewall): Aho-Corasick automaton scans all request fields:
  URI, header names/values, decoded body, trailers. Signatures loaded from policy file
  (default: security/waf/default-policy.txt, one pattern per line). Pattern match triggers
  SecurityError, returns 403 Forbidden, logs security event. Signature file reloadable.
  Status: Implemented. Evidence: security/waf/automaton.go, security/waf/policy.go

● Malformed Request Rejection: Detects and rejects invalid syntax, duplicate headers,
  both Content-Length and Transfer-Encoding, invalid chunks, missing Host header.
  Returns 400 Bad Request with appropriate error logging.
  Status: Implemented. Evidence: http/parser.go

● Connection Timeout: Enforces 5-second read deadline (anti-Slowloris protection).
  On timeout, closes connection and logs event. Prevents resource exhaustion attacks.
  Status: Implemented. Evidence: core/connection.go (conn.SetReadDeadline)

Configuration, Initialization & Logging
● Environment Variable Configuration: All configuration via environment variables
  (12-factor application pattern). Sensible defaults provided; warnings logged for
  invalid values (e.g., negative rates). No hardcoded secrets or credentials.
  Status: Implemented. Evidence: config/config.go

● WAF Policy Loading: Loads WAF signatures from text file at startup. Builds
  Aho-Corasick automaton before accepting connections. Supports pattern count logging
  and runtime configuration. Configurable via MTWS_WAF_POLICY_FILE.
  Status: Implemented. Evidence: security/waf/policy.go

● Startup Logging: Logs server address, port, worker pool size, job queue size,
  rate limiter config (rate, capacity, enabled/disabled status), WAF pattern count,
  and benchmark mode status. Provides visibility into configuration.
  Status: Implemented. Evidence: cmd/server/main.go (startup log messages)

● Request Logging: Logs each request with client IP:port, HTTP method, request path,
  HTTP version, and timestamp. Includes remote address for audit trail.
  Status: Implemented. Evidence: core/connection.go (log.Printf calls)

● Security Event Logging: Logs WAF matches: client IP, matched pattern, rule ID,
  scanned field, HTTP status code (403), timestamp. Supports security analysis.
  Status: Implemented. Evidence: core/connection.go (logSecurityEvent function)

● Parse Rejection Logging: Logs parsing errors: client IP, specific error reason,
  HTTP status code (400), timestamp. Aids in debugging malformed requests.
  Status: Implemented. Evidence: core/connection.go (logParseReject function)

Testing, Benchmarking & Deployment
● Unit Testing: Comprehensive tests for HTTP parser, WAF automaton, rate limiter,
  config parsing, and router logic. Invocation: go test ./... Tests verify correctness
  and edge cases.
  Status: Implemented. Evidence: *_test.go files throughout codebase

● Fuzz Testing: Fuzz tests for HTTP parser with malformed/random input to detect
  security regressions and edge cases. Invocation: go test -fuzz FuzzParseRequest ./http
  Status: Implemented. Evidence: http/parser_fuzz_test.go

● Benchmarking Tool (Lab): Integrated lab tool supporting:
  ○ Benchmark mode: load test with throughput/latency metrics, concurrent client simulation
  ○ Compare mode: parsing behavior comparison between MTWS and nginx+ModSecurity
  ○ Output: JSON results with RPS, latency percentiles (avg, P95, P99), success/failure counts
  Status: Implemented. Evidence: cmd/lab/main.go, cmd/lab/main_test.go

● Benchmark Payloads: Test payload suite in experiments/payloads/ including:
  ○ Benign payloads (health checks, simple GET requests)
  ○ Attack payloads (SQL injection, XSS, path traversal, header injection)
  ○ Chunked encoding edge cases and HTTP ambiguity scenarios
  ○ Format: Plain HTTP request files (.http extension)
  Status: Implemented. Evidence: experiments/payloads/ directory (17+ payload files)

● Docker Support: Dockerfile for containerized deployment. Exposes port 8080.
  Multi-stage build support. Alpine Linux base for minimal image size.
  Status: Implemented. Evidence: Dockerfile

● Docker Compose Stack: docker-compose.yml (MTWS + nginx+ModSecurity) and
  docker-compose.benchmark.yml (benchmark mode overrides). Volume mounts for
  policies and results. Enables reproducible multi-service testing.
  Status: Implemented. Evidence: docker-compose.yml, docker-compose.benchmark.yml

● Health Check Handler: /health endpoint returns 200 OK + "healthy" text.
  Used for container readiness probes and load balancer health checks.
  Status: Implemented. Evidence: cmd/server/main.go (healthHandler)

● Error Handling: Graceful error responses with appropriate HTTP status codes:
  400 Bad Request (malformed), 403 Forbidden (WAF), 404 Not Found (route),
  500 Internal Server Error (unhandled exception). Prevents information leakage.
  Status: Implemented. Evidence: core/response.go (writeErrorResponse)

6. DATA FLOW & ARCHITECTURE
==============================================

Request Processing Flow
1. TCP Listener accepts connection on configured port (default 8080)
2. Extract client IP from connection RemoteAddr
3. Rate Limiter evaluates token bucket for client IP
   - If tokens ≥ 1: deduct 1 token, proceed
   - Else: close connection immediately (silent rejection)
4. Post Job{connection, router} to buffered job queue (capacity 200)
5. Worker from pool (10 workers, configurable) dequeues job
6. Connection Handler sets 5-second read deadline
7. Parse HTTP/1.1 request via bufio reader
8. WAF scans all fields (URI, headers, body, trailers)
   - Match found → return SecurityError → 403 Forbidden + security log
9. Parse error → return 400 Bad Request + parse rejection log
10. Router extracts path and looks up registered handler
    - Not found → 404 Not Found
    - Found → execute handler function
11. Response Writer buffers status + headers, writes body, flushes to socket
12. Connection closes (defer); resources cleaned up; worker ready for next job

Queuing & Backpressure
● Buffered Job Queue: 200-capacity channel between listener and worker pool
● Listener Blocking: When queue full, listener blocks on send; natural rate control
● Worker Blocking: When queue empty, worker blocks on receive; efficient CPU usage
● No Unbounded Growth: Fixed worker count + bounded queue prevent resource exhaustion

Key Performance Paths
● Parse → WAF Scan: ~1-5 ms per request (depends on body size, pattern count)
● Queue Latency: <1 ms typical (instant if slot available)
● Worker Dispatch: <1 ms (goroutine context switch)
● Total Request Path: Parse + Route + Handler execution + Response write

7. SECURITY SCANNING PIPELINE
==============================================

WAF Scanning Scope
Field              | Scanned | When                    | Impact
URI                | Yes     | During request line parse  | Prevents SQLi/XSS/traversal
Header names       | Yes     | During header parse     | Detects header injection
Header values      | Yes     | During header parse     | Scans cookie, auth, etc.
Body bytes         | Yes     | During body/chunk parse | HTTP layer injection detection
Trailer names      | Yes     | During trailer parse    | Edge case scanning
Trailer values     | Yes     | During trailer parse    | Completes coverage

Scanning Pattern
Request arrives → Parse request line
             ↓
Parse headers (scan each name/value)
             ↓
Parse body (scan decoded bytes)
             ↓
Parse trailers (scan trailer name/value pairs)
             ↓
Any match → SecurityError → 403 Forbidden + security log
No match → Continue to routing
